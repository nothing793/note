## 1. §3.1 流水线概览：为什么流水线会“出错”（p.2–24）

### 1.1 先问一个问题：流水线能否保证每条指令都正确执行（p.4）【讲义】

结论不是“天然正确”，而是需要额外整合：

- 结构冒险（Structural Hazard）：**资源忙**，多个指令同时要用同一个部件；
- 数据冒险（Data Hazard）：**指令之间依赖前一条指令的结果**；
- 控制冒险（Control Hazard）：**分支导致下一条指令未知**，程序流向依赖前一条指令。

也就是说，流水线的本质是“让多条指令重叠”，但重叠会带来资源竞争、依赖冲突与分支判断问题。这也是efficiency到达不了1的原因。

### 1.2 结构冒险（Structural Hazard，p.6–9）【讲义】

- 典型例子：**单个 memory**，同时要读取指令和数据。
- 这时 IF 阶段和 MEM 阶段都要访问存储器，资源冲突。
- 解决方案：
  1. **加硬件**：指令存储器 / 数据存储器分开（Harvard structure）；
  2. **让指令轮流使用**：加入 `NOP` / stall，等待资源空闲。

关键点：

- 结构冒险本质上是“所需部件被占用”；
- 不能靠编译器直接消除，通常需要硬件支持或优化微架构。

### 1.3 数据冒险（Data Hazard，p.10–17）【讲义】

#### 1.3.1 最基础例子

```asm
add  x1, x2, x3
sub  x4, x1, x5
```

- `sub` 要用 `x1`，而 `x1` 是前一条 `add` 写回的结果；
- 若 `sub` 在 EX 阶段读取 `x1` 时，`add` 还没完成写回，则会读到旧值。
- 这种依赖就是**数据冒险**。

#### 1.3.2 直接 stall

- 最简单的办法：让 `sub` 在 ID/EX 阶段停一拍，等 `add` 先写回，再继续执行。
- 这会引入 pipeline bubble（气泡）。

#### 1.3.3 forwarding / bypass

- 当 `add` 已经算出 ALU 结果，但还没写回寄存器时，可把结果直接从**ALU 输出**送回后续指令。
- 这称为 **forwarding**（转发）或 **bypass**。
- 例子：`add` 已经在 EX 中产生结果，`sub` 需要用它，这时不必等到写回寄存器。

#### 1.3.4 不能完全靠转发：Load-Use Hazard

```asm
load  x1, 0(x2)
sub   x4, x1, x5
```

- `load` 需要先从内存读到 `x1`，然后 `sub` 才能使用它；
- 仅靠 ALU 转发无法提前补齐数据，因为数据来自内存，而不是 ALU 输出。
- 因此，**load-use hazard 需要至少一拍 stall**，等 `load` 进入 WB 后再转发。

#### 1.3.5 代码重排（reordering）

例题里给了 C 代码：

```c
a = b + e;
c = b + f;
```

生成的 RISC-V 代码中，若按原顺序执行，`add` 与后续 `add` 之间有依赖；
可通过调换指令顺序，让 `ld x1, 0(x31)`、`ld x2, 8(x31)`、`ld x4, 16(x31)` 先各自装载，再进行两次加法计算，就能**消除部分 hazards**，减少 stall。

> 这类重排属于编译器优化和指令调度（instruction scheduling），它和硬件 forwarding 互相配合。

### 1.4 控制冒险（Control Hazard，p.18–23）【讲义】

- 典型场景：`branch` 指令需要判断是否跳转；但 IF 阶段要拿下一条指令，**提前不知道下一条应该是什么**。
- 因而分支会导致控制冒险。

#### 1.4.1 直接 stall

- 如果分支条件还没有算出，就无法知道它是否跳转；
- 最朴素办法：**插入气泡**（stall），等分支判断完成后再取下一条指令。
- 这会产生两个 bubble。

#### 1.4.2 静态分支预测

- **always not taken**：简单但不精确；
- **always taken**：适用于循环尾部分支；
- 在很多体系结构中，分支预测依赖历史记录。

#### 1.4.3 动态分支预测

- 依据最近几次分支执行历史，预测未来是否 taken；
- 这是现代处理器的关键设计之一。

#### 1.4.4 重点收敛

- 结构冒险：资源冲突；
- 数据冒险：数据依赖；
- 控制冒险：分支流向不确定；
- 不同冒险的处理手段不同：stall、forwarding、预测、重排。

### 1.5 小结（p.24）【讲义】

- 流水线是“指令间重叠执行”的实现技术；
- 它提高的是**吞吐率/并发度**，而不是单条指令本身的执行速度；
- 设计者必须处理：**结构、控制、数据**三类 hazard；
- 流水线对程序员通常是**透明的**：程序看起来还是顺序执行，实际是并行重叠。

## 2. §3.2 流水线数据通路（Pipelined Datapath，p.25–62）

### 2.1 从单周期数据通路到流水线（p.25–35）【讲义】

- 单周期数据通路中，指令从 IF → ID → EX → MEM → WB 的各阶段都在一条路径上串行走一轮；
- 但如果要让多条指令重叠，就不能简单共享同一个单周期数据通路。
- 解决思路：**在各阶段之间加入流水寄存器**（pipeline register）保存阶段间状态。

关键原则：

- 早阶段的输出要存入寄存器；
- 后续阶段取出数据继续处理；
- 这样不同指令能在不同阶段同时前进。

### 2.2 两个“例外”导致冒险（p.26–29）【讲义】

讲义里指出单周期数据通路中有两个关键例外：

1. **写回寄存器**时，下一条指令可能还在使用这一状态；
2. **分支指令**使得程序流在 IF 阶段就要决定下一条地址。

这正是后面数据冒险和控制冒险的源头。

### 2.3 流水线寄存器：把数据从前一阶段送到后一阶段（p.34–49）【讲义】

- `IF/ID`：保存当前指令与 PC；
- `ID/EX`：保存读寄存器号、立即数、控制信号等；
- `EX/MEM`：保存 ALU 结果、分支目标、写回寄存器号等；
- `MEM/WB`：保存内存读结果、写回寄存器号等。

#### 2.3.1 Load 指令

- `IF` 取指令；
- `ID` 译码并读取寄存器；
- `EX` 计算地址；
- `MEM` 访问存储器；
- `WB` 将读到的数据写回寄存器。

#### 2.3.2 Store 指令

- `IF` 取指令；
- `ID` 译码；
- `EX` 计算地址；
- `MEM` 把数据写入内存；
- `WB` 可视为无实际写回动作，或者不再使用。

### 2.4 一个关键 bug：Load 的写回寄存器号可能错（p.49–56）【讲义】

这里是本讲最关键的细节之一：

- 如果只把 `ID/EX` 中的 `Rd` 直接传到 `MEM/WB`，而另一条后续指令改写了 `ID/EX` 中间寄存器，就可能发生“写回寄存器号被覆盖”的问题。
- 也就是说，**写回目标寄存器号也必须跟着流水线寄存器一起传递**，不能只保留一个临时值。

因此，真正正确的实现方法是：

- 把 `write register number` 也放到适当的 pipeline register 中；
- 这样在 WB 阶段才知道“到底该写回哪个寄存器”。

### 2.5 图示化表示流水线（p.57–62）【讲义】

- 讲义把多个时钟周期下的指令执行过程画成单时钟周期管线图；
- 这类图能清晰展示：
  - 不同指令在不同阶段重叠；
  - 每个阶段所持有的寄存器、存储器状态；
  - 这些状态如何在时钟边沿更新。

几个重点：

- 每条指令在每个周期只占一个 stage；
- 只要通过流水寄存器保存中间状态，指令间就能 “看起来” 顺序执行、实际上并行重叠。

## 3. §3.3 流水线控制（Pipelined Control，p.63–75）

### 3.1 控制信号如何沿流水线传递（p.63–75）【讲义】

讲义强调：

- **IF 和 ID 阶段不需要额外设计新控制器**；
- 关键是把控制信号从原来的单周期设计中“向后扩展到各个流水阶段”。

即：

- EX 阶段使用的控制信号负责 ALU 运算类型；
- MEM 阶段需要负责 branch/ld/stores；
- WB 阶段负责寄存器写回。

### 3.2 典型控制线

#### 3.2.1 EX 级控制信号

- `ALUOp`：决定 ALU 做什么运算；
- `ALUSrc`：决定第二个操作数来自寄存器还是立即数；
- `Op`/`funct` 等：指导指令类型判断。

#### 3.2.2 MEM 级控制信号

- `Branch`：是否为分支指令；
- `MemRead`：是否读内存；
- `MemWrite`：是否写内存；
- `Jump` 等：控制流水中某些指令流向变化。

#### 3.2.3 WB 级控制信号

- `RegWrite`：当前阶段是否写回寄存器；
- `MemToReg`：写回值来自内存还是 ALU。

### 3.3 统一控制思想

- 控制信号不再只在单一阶段产生；
- **它们必须在对应流水寄存器中保存并向后传递**。
- 这样每个阶段只需读取自己的控制字，而不需要去猜测前后指令的状态。

这相当于把“控制器”拆散到各个 stage，形成了“流水线控制”。

## 4. §3.4 用 stall 处理流水线冒险（Pipelining with Stall，p.76–85）

### 4.1 数据冒险如何检测（p.77–79）【讲义】

讲义给出了非常典型的检测方式：

- 沿着流水线传递寄存器号（`Rs1`, `Rs2`, `Rd`）；
- 在 EX 阶段判断：

```text
EX/MEM.Rd = ID/EX.Rs1
EX/MEM.Rd = ID/EX.Rs2
```

- 但必须满足：
  - 当前指令确实要写寄存器（`RegWrite`）；
  - 目标寄存器不是 `x0`；
  - 目标寄存器号不为空。

这就是 hazard detection 的核心逻辑：**用寄存器编号做“依赖判断”**。

### 4.2 处理方法：stall 或 forwarding（p.80–82）【讲义】

#### 方式 1：stall

- 当 hazard 检测到依赖时，
  - 令 `EX/MEM` 中控制信号清零；
  - 让 EX / MEM / WB 都变成 `NOP`；
  - 并阻止 PC 与 IF/ID 更新；
- 这样下一条指令会被重新取回并解码，形成 1-cycle stall。

#### 方式 2：forwarding

- 当依赖项已经在 ALU 结果中产生时，直接把结果转发到下一条指令；
- 这避免了“空等”一拍，提高性能。

### 4.3 对 load-use hazard 的特殊处理（p.82）【讲义】

- 对 `load` 后接 `use` 的情况，单纯转发还不够；
- 必须让后一条指令 stall 一拍，等 memory 数据真正读到寄存器中。
- 之后 can subsequently forward to EX stage（随后可转发给 EX 阶段）。

这个机制是现代流水线调度里最关键的细节之一：

- **forwarding 解决 ALU 结果依赖**；
- **stall 解决 load-use 的“等待内存读取”问题**。

### 4.4 bubble 的本质（p.83–85）【讲义】

- `bubble` 就是“空指令（NOP）”插入流水线；
- 它不改变程序语义，但消耗一个周期来等待资源/依赖；
- pipeline bubble 是流水线正确性与性能之间的平衡体操。

## 5. 听课重点与易混点

### 5.1 结构冒险 vs 数据冒险 vs 控制冒险

- 结构冒险：**资源不够**；
- 数据冒险：**结果还没写回就被后续使用**；
- 控制冒险：**指令流依赖分支判断**。

### 5.2 转发与停顿不是对立，而是互补

- 需要时，转发提高效率；
- 不能转发时，就 stall；
- 现代 CPU 很多时候是「hazard detection + forwarding + stall」三者并用。

### 5.3 流水寄存器是关键

- 没有流水寄存器，流水线就不成立；
- 所有中间状态都必须严谨保存到各级寄存器中，才能保证正确性。

### 5.4 流水线不像“单周期的复制粘贴”

- 代码不再看起来是“一个时钟周期执行一条指令”；
- it is a set of simultaneously active stages for different instructions.
