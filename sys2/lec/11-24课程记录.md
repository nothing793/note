## 二、进程的概念

进程是一个 **unit of resource**，主要跟资源相关：

- 资源包括 memory、CPU
- 所以进程是 **unit of resource allocation and protection**（资源分配与保护单元）

后面讲线程时会对比：线程是**执行单元**。面试常问“线程和进程有什么区别”，这里先埋下伏笔。

一个进程包含：

- code 和 data section，由 ELF 映射到内存
- 运行时内存，其中两块重要区域：**栈（stack）** 和 **堆（heap）**
- 运行时寄存器

进程切换时，重点切换的是**栈**和**寄存器**。寄存器只有一份，所以必须保存和恢复。

课堂展示了一个进程的内存空间图，可以看到一个 C 函数里各个变量分别落在哪个区域。这是 C 语言的 memory model，属于 C 语言进阶内容。

## 三、栈（Stack）

栈里每一块称为 **stack frame**，每个函数有自己的 stack frame。栈从高地址向低地址增长。

栈由两个寄存器指向：

- **SP**：指向栈顶（当前 stack frame 的顶）
- **FP**：指向当前 stack frame 的底

栈的“尾巴”（最高地址）由 `task_struct` 里的 `stack` 变量加上栈大小得到，即栈的最顶部。

栈完美解决了函数调用问题：再多函数调用，栈也能处理；但不能无限调用，否则栈会 **overflow**（溢出）。

同一个 ELF 运行两次，会得到不同的栈：大小大概率不同、内容也不同；heap 也不一样。但 ELF 映射的部分大小一样，内容八成不一样。

---

## 四、PCB（进程控制块）

PCB 里存放进程的元数据，包括：

- 进程状态
- 进程号 PID
- program counter
- 运行时寄存器
- memory limits
- open files

这就是“运行的上下文”。Linux 里 PCB 就是 `task_struct`，用链表（list head）串起来。

---

## 五、进程的五个状态

要记住那张状态图：

- **new**：新建
- **ready**：就绪
- **running**：运行
- **waiting / blocked**：等待事件（如等磁盘 I/O）
- **terminated**：终止

运行时间片跑完回到 ready；等事件时移到 waiting，事件完成再回到 ready。

重点讲了两个系统调用：

- **fork**：没有参数，把 parent 的内存原封不动拷贝一份
- **exec**：把 parent 的 memory space 全部清掉，换成自己的

终止状态：parent 要用 **wait** 回收 child，也可以用信号 terminate。zombie 状态是 PCB 没有被 parent 回收；orphan（孤儿）是 parent 已退出，进程被 PID 1 或类似 init 收养。

三个运行态中哪些有队列：

- **ready 有队列**，叫 ready queue，一般系统一个 ready queue，所有 CPU 从里面取
- **waiting 有队列**，每个被等待的对象都有自己的 waiting queue
- running 没有队列

PCB 通过调整链表指针在不同队列之间移动。

## 六、上下文切换（Context Switch）

进程切换发生两次上下文切换。上下文有两种：

- **user space 上下文**
- **kernel space 上下文**

`cpu_switch_to` 这个函数切换的是 **kernel space 上下文**，里面切的都是 kernel space 的指针和数据。

### 1. kernel space 上下文

为什么只从 X19 保存到 X30（X30 即 LR）？因为 X0–X18 在调用 `cpu_switch_to` 之前已经被 calling convention 保存了，所以这里只需保存 callee-saved 寄存器。

kernel space 上下文被保存到哪里？保存到 **PCB** 里，更详细地说，是 `task_struct` 里的 `cpu_context` 数据结构。注意这是 ARM 上；RISC-V 上也保存到 PCB，但 `cpu_context` 跟着架构走，不同架构寄存器名字和个数都不一样。

### 2. `cpu_switch_to` 的两步关键

以 Linux 4.14 ARM 版本为例，函数原型第一个参数 `prev` 放在 X0，指向要被换出的进程 PCB；第二个参数 `next` 指向要被换入的进程 PCB。

关键步骤：

1. 计算 `cpu_context` 在 `task_struct` 中的偏移量，放到 X10，再与 PCB 指针相加得到地址，存入 X8。
2. 用 `stp` 一对一对地保存 X19/X20、X21/X22……直到 X29（FP），再保存 X9，最后保存 LR（返回地址）。
3. 换入时，X8 指向新进程的 `cpu_context`，用 `ldp` 一对一对 load 回来，单独 load LR 和 X29，把 stack pointer 挪到 SP，完成**栈切换**。
4. 最后 `ret` 跳到 LR 内容继续执行，完成**代码切换**。

所以整个切换 = 栈切换 + 代码（PC）切换 + return。

### 3. PC 什么时候被设置？

`cpu_context` 里的 PC 有两种情况被设置：

1. 上一次 `cpu_switch_to` 把它换出去时，保存的是 `cpu_switch_to` 的 caller 地址。
2. 进程第一次创建时：`copy_thread` 里设置 PC 为 `ret_from_fork`；`exec` 时也会设置 PC。

### 4. user space 上下文

user space 上下文保存在**栈的最高地址**（栈开始的位置），包含 31 个寄存器，SP、PC 等都有。

从 user space 进内核时，`kernel_entry` 会把所有寄存器保存一遍（一对一对 `stp`）。教师提到当年在 4.14 这个文件里发现过一个 bug：少写了一个反斜杠，导致判断条件不成立，中间代码没被编译进去，后来修了。

关键陷阱：P0 进内核时，user space 上下文保存到 **P0 的内核栈**；做完 `cpu_switch_to` 后已经是 P1 了，回到 user space 时必须从 **P1 的内核栈** load user space 上下文。不能从 P0 的栈 load，否则会 segment fault。

P1 的 user space 上下文什么时候 save 的？两种答案：

1. 上一次它被换出去时，从 user space 进来时 save 的。
2. 它是 fork 出来的，直接拷贝 parent 的。

### 5. 系统调用的上下文切换次数

一次进程切换的完整上下文切换：user space → kernel space 一次，kernel space 里 `cpu_switch_to` 一次，再回 user space 一次。面试问“发生了几次”，答一次的人往往忘了 user/kernel 这次；能答三次并说清楚很难，说明内核功力扎实。

如果只是系统调用（syscall），不涉及 `cpu_switch_to`：进 kernel space 一次、回 user space 一次，共两次，且都是 P0 自己的上下文。

## 七、fork 为什么返回两个值

fork 返回值放在 **pt_regs 里的 X0**。fork 之后有两个进程、两套 pt_regs、两个 X0：

- parent 的 X0 被设置成 child 的 PID
- child 的 X0 被设置成 0

parent 返回值在 `copy_process` 相关代码里把 X0 存到栈上（注释 `return X0`），最终从 X0 返回 user space。

child 这边：

- `pt_regs` 的 X0 被设成 0
- kernel space PC 被设成 `ret_from_fork`
- user space PC 完整拷贝 parent，和 parent 一模一样

exec 时：user space PC 被设成新 ELF binary 的 entry（ELF header 里的 entry），这正是 `load_elf_binary` 改 `pt_regs` 里 PC 的地方。kernel space PC 在 exec 时不动，仍是上次被换出去时保存的值。

## 八、Linux 0.11 的进程管理

1991 年 Linux 0.11：

- `task_struct` 定义在 `include/linux/sched.h`，只有二三十行
- 最大进程数固定：**NR_TASKS = 64**
- 所有 PCB 放在一个固定数组 `task[64]` 里，元素是指针
- **没有 list_head 概念**，没有 ready queue、waiting queue
- 选下一个 ready 进程：遍历这个 64 元素数组
- 找 sleep 的进程：也是遍历数组

`schedule()` 函数：从数组尾部往前遍历，找到可运行进程，最后靠 `switch_to` 做上下文切换。0.11 的 `switch_to` 定义在头文件里，是一个宏，内联汇编换寄存器，类似写一个 C 函数。

---

## 九、Linux 2.3.0（1999 年）的演进

- 有了 **list_head** 概念
- 有匿名队列，用 `task_struct` 里的 `prev_run` / `next_run` 链接
- 仍有固定 PCB table，但大小变成 **512**
- 有 `schedule()` 函数，`switch_to` 名字沿用至今
- 有具名 waiting queue，如 `motor_wait`

`task_struct` 不到 100 行（约 1000 多行上下文里的一部分）。ready queue 用双向链表维护。

`switch_to` 的定义：**每个硬件架构一个**。x86、ARM、RISC-V 的寄存器名字和指令都不一样，所以每个架构各定义一份。

2.3.0 里有个 `motor_wait` 队列，是等软盘马达转起来的等待队列。教师科普：硬盘之前有软盘，软盘很软，插入电脑后马达转动读盘；“motor wait”就是等软盘马达。现在相当于等硬盘或 SSD。

`sleep_on` 函数：

- 把当前进程状态改成 `TASK_INTERRUPTIBLE`（或 waiting）
- 把进程加到 waiting queue 头部或尾部
- 调用 `schedule()`

`schedule()` 的效果：当前进程要 sleep，让出 CPU；找一个 ready 进程，做上下文切换，把 CPU 给 ready 进程。注意不是找“下一条能跑的指令”，而是找“下一个处于 ready 状态的进程”。

## 十、课堂结论与作业

- 进程切换 = 栈切换 + 代码（PC）切换 + return
- kernel space 上下文存 PCB 的 `cpu_context`
- user space 上下文存内核栈最高地址
- fork 两个返回值靠两套 pt_regs 的 X0
- exec 设置 user space PC 为 ELF entry
- Linux 0.11：固定 64 进程数组，无链表，遍历选进程
- Linux 2.3.0：有 list_head、512 PCB table、具名等待队列
- 课件已放出，学生需下去看 Linux 0.11 / 2.3 源码，参考 Linux Cross Reference
